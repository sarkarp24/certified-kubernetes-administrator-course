1. What is Containerization?

Containerization is a technology used to package an application along with everything it needs to run, such as:

Application code
Libraries
Frameworks
Dependencies
Runtime components
Configuration

The packaged unit is called a container image.

From that image, we can create and run containers.

Image vs Container

Think of it like this:

Container Image
      │
      │ run
      ▼
   Container
Image → static/package/template
Container → running/execution instance of an image

For example:

MySQL Image
     │
     ├── Container 1
     ├── Container 2
     └── Container 3

The same image can be used to create multiple containers.

2. Container Technologies

Some commonly used container engines/runtimes are:

Docker
containerd
CRI-O
Podman

For example:

MySQL Application
       ↓
   Container Image
       ↓
 Docker Hub / Private Registry
       ↓
   Container

A container image can be stored in a container registry such as Docker Hub.

3. Example — Operating System Image vs Container Image

The concept of an image is not unique to containers.

For example, on a Windows laptop:

Windows ISO
     ↓
Installation
     ↓
Windows OS

A Windows .iso file is an image containing the files required to install the operating system.

Similarly, with containers:

Application
     ↓
Container Image
     ↓
Container

A container image contains the application and the required dependencies.

4. What Does a Container Image Contain?

A container image can contain:

Application
    +
Libraries
    +
Frameworks
    +
Runtime
    +
Dependencies

For example, a custom Java application might have:

Java Application
      +
JRE
      +
Required Libraries
      +
Configuration
      ↓
Container Image

DevOps teams build these images and store them in a container registry.

The same image can then be used consistently across different environments:

Development
     ↓
Testing
     ↓
Staging
     ↓
Production
5. What is Kubernetes?

Kubernetes, commonly abbreviated as K8s, is a container orchestration platform.

It is used to deploy, manage, scale, and maintain containerized applications across multiple machines.

Instead of manually managing containers on individual servers, Kubernetes manages them as a cluster.

Without Kubernetes
Server 1
 └── MySQL Container

Server 2
 └── Nginx Container

Server 3
 └── Kafka Container

If Server 1 fails, the MySQL container is also unavailable.

This can create a Single Point of Failure (SPOF).

With Kubernetes
             Kubernetes Cluster
                    │
       ┌────────────┼────────────┐
       │            │            │
    Node 1        Node 2       Node 3
       │            │            │
     Pods         Pods         Pods

Kubernetes can provide capabilities such as:

Container orchestration
Scheduling
Scaling
Self-healing
High availability
Service discovery
Load balancing
Rolling updates
Automated container management
6. Kubernetes History

Kubernetes originated at Google and was influenced by Google's internal container-management systems, particularly Borg.

A simplified history:

Google
  │
  │ Container orchestration experience
  ↓
Borg / internal systems
  │
  ↓
Kubernetes
  │
  ↓
CNCF
  │
  ↓
Open-source ecosystem

Important dates:

2014 → Kubernetes was introduced by Google as an open-source project.
2015 → Kubernetes 1.0 was released.
Kubernetes was donated to the Cloud Native Computing Foundation (CNCF).
Kubernetes is primarily developed using the Go programming language.

Note: The original notes saying "2009–2013 Kubernetes was an internal project" are not quite accurate. Google had internal systems such as Borg before Kubernetes; Kubernetes itself was publicly introduced in 2014.

7. What is CNCF?

CNCF = Cloud Native Computing Foundation

CNCF is part of the Linux Foundation and hosts/governs many important cloud-native open-source projects.

Examples include:

Kubernetes
Prometheus
etcd
CoreDNS
Envoy

Think of CNCF as an ecosystem/foundation supporting cloud-native projects and their communities.

8. Kubernetes Architecture

A Kubernetes cluster is a collection of machines called nodes.

These nodes communicate over a network.

A simplified architecture:

                 Kubernetes Cluster
                         │
          ┌──────────────┴──────────────┐
          │                             │
    Control Plane                   Worker Nodes
          │                             │
    ┌─────┴─────┐              ┌───────┼───────┐
    │           │              │       │       │
 API Server  Scheduler        Pod     Pod     Pod
    │
 Controllers
    │
   etcd

A Kubernetes cluster traditionally has two major types of nodes:

Control Plane
Worker Nodes
9. Control Plane

The Control Plane is responsible for managing the Kubernetes cluster.

Major components include:

1. kube-apiserver

The API server is the main entry point to the Kubernetes cluster.

For example:

kubectl
   ↓
kube-apiserver

It receives requests and communicates with other Kubernetes components.

2. Scheduler

The kube-scheduler decides which worker node should run a Pod.

Example:

New Pod
   ↓
Scheduler
   ↓
Worker Node 2
   ↓
Pod runs here
3. Controller Manager

Controllers continuously watch the cluster and try to make the actual state match the desired state.

For example:

Desired:
3 Pods

Actual:
2 Pods

Controller
   ↓
Creates another Pod
   ↓
Actual = 3 Pods
4. etcd

etcd is the distributed key-value store used by Kubernetes to store cluster state and configuration data.

Conceptually:

Kubernetes State
       ↓
      etcd
10. Worker Node

Worker nodes are where application workloads actually run.

Examples:

Worker Node
    │
    ├── Pod
    │    └── Nginx Container
    │
    ├── Pod
    │    └── MySQL Container
    │
    └── Pod
         └── Kafka Container

Worker nodes contain components required to run Pods, including a container runtime and the Kubernetes node agent (kubelet).

11. Control Plane vs Worker Node
Control Plane	Worker Node
Manages the cluster	Runs workloads
API Server	kubelet
Scheduler	Container runtime
Controller Manager	Pods
etcd	Application containers
Decides where Pods should run	Actually runs Pods
12. What is a Pod?

A Pod is the smallest deployable unit in Kubernetes.

A Pod provides an execution environment for one or more containers.

The important relationship is:

Kubernetes
    ↓
   Pod
    ↓
Container(s)

A Pod is not exactly the same thing as a container.

Usually
Pod
 └── Container

But a Pod can also contain multiple tightly coupled containers:

Pod
 ├── Application Container
 └── Sidecar Container

Containers inside the same Pod share certain resources, such as:

Network namespace
Pod IP address
Volumes mounted into the Pod
13. Kubernetes and Container Runtime

A common misconception is:

"Kubernetes directly runs Docker containers."

More accurately, Kubernetes uses a container runtime to run containers.

Modern Kubernetes uses runtimes that implement the Container Runtime Interface (CRI), commonly:

containerd
CRI-O

The relationship is roughly:

Kubernetes
     │
     │ CRI
     ↓
Container Runtime
     │
     ↓
Containers

Docker Engine is no longer directly supported as a Kubernetes runtime through the old dockershim mechanism.

However, Docker remains extremely common for building container images.

14. kubectl

kubectl is the command-line interface (CLI) used to interact with a Kubernetes cluster.

Conceptually:

Administrator
      │
      ↓
   kubectl
      │
      ↓
kube-apiserver
      │
      ↓
Kubernetes Cluster

For example:

kubectl get nodes

Displays the nodes in the cluster.

15. Creating Your First Pod

Example:

kubectl run firstpod --image=httpd

This tells Kubernetes:

Create a Pod named firstpod using the httpd container image.

Conceptually:

kubectl run firstpod --image=httpd
                │
                ↓
          kube-apiserver
                │
                ↓
            Scheduler
                │
                ↓
          Worker Node
                │
                ↓
              Pod
                │
                ↓
        httpd Container

You can verify it with:

kubectl get pods
